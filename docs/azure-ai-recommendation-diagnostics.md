# Azure AI 추천 진단 (2026-10-14)

## 증상과 확인 결과

관리자 테마 화면에서 색상 추천과 두 배경 추천이 HTTP 504로 실패했다. 백엔드 OpenAI 요청 제한은 45초, 브라우저는 60초, Nginx는 75초였다. 같은 VM의 별도 Java 요청은 성공했지만, 실행 중인 애플리케이션의 실패 원인을 설명할 로그가 없었다.

두 OpenAI 클라이언트에 진단 로그를 추가하고 백엔드만 재배포한 뒤 실제 관리자 화면에서 확인했다.

| 요청 | 결과 | 백엔드 OpenAI 처리 시간 |
| --- | --- | --- |
| 테마 최초 추천 | HTTP 200 / HTTP_2 | 8.544초 |
| ticket 배경 추천 | HTTP 200 / HTTP_2 | 4.123초 |
| closed 배경 추천 | HTTP 200 / HTTP_2 | 3.938초 |
| 같은 프로세스에서 테마 재추천 | HTTP 200 / HTTP_2 | 6.615초 |

첫 세 요청은 화면에서 동시에 실행됐다. 두 번째 추천에서는 성공한 배경을 프론트 캐시에서 재사용했다. 화면에 유효한 원본형 시안이 표시됐으며, 다른 후보는 기존 색상 검증 규칙에 따라 제외됐다. 진단 작업에서 저장·전체 적용은 실행하지 않았다.

**재배포/프로세스 재시작 후 정상 동작은 확인했지만, 이전 타임아웃의 근본 원인은 확정하지 못했다.** 이번 변경은 관측 기능 추가이며, 타임아웃이나 전송 프로토콜을 바꾸지 않았다. HTTP/2 자체, 요청 크기, 동시 요청을 원인으로 단정하거나 영구 해결됐다고 해석하면 안 된다.

## 로그 범위

`OpenAiThemeRecommendationClient`, `OpenAiPosterFocusClient`가 다음 항목만 기록한다.

- 호출별 임의 UUID, 작업 종류, 검증된 배경 target
- 이미지 바이트 수, 모델/엔드포인트 설정 여부
- HTTP 상태, 협상된 프로토콜, 경과 시간
- 성공/오류 코드, 전송 실패의 예외 클래스명

API 키, 인증 헤더, URL/SAS, 프롬프트, 포스터 Base64, 업스트림 응답 본문 및 예외 메시지/스택은 이 진단 로그에 기록하지 않는다. 설정 여부는 값이 존재한다는 뜻이며 올바른 모델·엔드포인트라는 검증은 아니다.

VM에서 안전한 진단 항목만 조회하려면:

```sh
sudo docker logs --since 10m danzzan-azure-app-1 2>&1 | grep 'AI recommendation'
```

`start` 이후 `response` 없이 `OPENAI_TIMEOUT`이면 OpenAI HTTP 호출 중 시간 초과다. `response`의 상태가 429이면 요청 제한, 다른 비정상 상태면 업스트림 오류를 구분한다. `SUCCESS`는 클라이언트 응답 파싱 성공이며 이후 팔레트 검증이나 이미지 렌더링까지 보장하지 않는다. 로그 공유 시 전체 컨테이너 로그 대신 이 항목만 사용한다.

## 배포·보존·검증

- 수정한 두 운영 클라이언트 파일만 VM에 전달하고 `app` 이미지를 빌드·교체했다. Nginx는 백엔드 주소 갱신을 위해 설정 검사 후 reload했다.
- MySQL·Redis·Kafka 컨테이너 ID가 유지됐고, 새 배포 직전과 실제 화면 검증 후의 콘텐츠·이미지 참조·설정·테마 20개 테이블 해시가 일치했다. Blob 쓰기·삭제나 DB 변경은 수행하지 않았다.
- 최초 보호 검사에서는 준비 이후 별도로 실행된 홈 이미지 추가·순서 변경 요청 때문에 해시가 달랐다. 백엔드 이미지만 자동 롤백했으며 DB를 되돌리지 않았다. 최신 저장 상태를 기준으로 재배포한 이후 비교는 일치했다.
- 비밀값 노출 방지 회귀 테스트를 포함해 `ThemeRecommendationTest` 23건, `OpenAiPosterFocusClientTest` 4건이 통과했다. Docker 빌드, app health, 공개 HTTPS `/api/health`, `git diff --check`도 통과했다.
- 복구 경로: `/opt/danzzan/deployment-backups/20261014-ai-diagnostics`. 이전 소스는 `sources-before.tar.gz`, 이전 이미지 태그는 `danzzan-be:rollback-20261014-ai-diagnostics`다. 스키마 변경이 없으므로 애플리케이션 롤백에 DB 복원은 필요 없다.

재발하면 먼저 발생 시각과 위 로그의 호출 UUID/시간/상태를 확인한다. 원인 증거 없이 타임아웃 연장이나 자동 유료 재시도를 추가하지 않는다.

## 2026-10-21: 시간 제한 연장 후 재발

`20261021-theme-timeout` 배포로 색상 추천의 BE 제한을 150초, FE와 Nginx 제한을 180초로 늘린 뒤에도 시간 초과가 재발했다. 실행 app 이미지와 시작 시각(08:47:42 UTC)을 확인했으며, 해당 컨테이너의 조회 시점 로그에는 색상 클라이언트 처리 성공 5건·시간 초과 4건, 배경 생성 성공 2건·시간 초과 4건이 있었다. 여기서 색상 `SUCCESS`는 응답 파싱까지 성공했다는 뜻으로 최종 팔레트 검증 성공과 구분한다.

- 22:39~22:45 KST의 실패 요청은 약 150,000ms 뒤 `OPENAI_TIMEOUT`으로 끝났다. 새 제한이 적용되지 않은 문제는 아니다.
- 동일 포스터(2,268,583바이트)의 색상 추천과 ticket/closed 배경 생성에서 모두 응답 로그 없이 시간 초과가 발생했다. 반복된 색상 추천 요청 일부는 앞 요청이 끝나기 전에 시작됐다.
- 재발 로그 조회 당시 운영 색상 모델은 `gpt-4o-mini`였고 두 API 모두 공식 OpenAI 엔드포인트를 사용했다. 키 존재 여부만 확인했으며 키 유효성이나 계정 한도는 이 검사로 입증되지 않는다.
- 모델 지원 종료, HTTP/2 연결 재사용, 이미지 크기, 동시 요청 중 어느 것이 원인인지는 아직 확정하지 않았다. 추가 시간 연장이나 자동 재시도는 적용하지 않았다.

후속으로 사용자 요청에 따라 새 키와 색상 모델 `gpt-6-luna`, `reasoning.effort=none`을 Azure에 적용했다. 공식 [종료 일정](https://developers.openai.com/api/docs/deprecations)은 GPT-4o mini의 종료일을 2027-01-14로 안내하므로, 이번 실패를 이미 종료된 모델 호출로 해석하면 안 된다. 권장 대체 모델 [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)는 이미지 입력과 Structured Outputs를 지원한다. `none`은 기존 2,400 출력 토큰 한도를 내부 추론에 소모하지 않도록 명시했다.

새 키로 모델 조회 HTTP 200, 실행 컨테이너의 새 키·모델·추론 설정과 healthy 상태를 확인했다. 사용자는 실제 시안 생성 성공을 알렸고 화면에서도 추천 완료를 확인했지만, 그 결과를 새 설정 적용 이후 요청과 연결하지는 못했다. 이후 사용자 요청으로 추가 생성 검증을 중단했으며 검증용 화면에서는 대표색 추출까지만 실행했다. 따라서 새 모델의 실제 생성 성공이나 시간 초과 문제의 해소를 확인한 기록으로 해석하면 안 된다. 배포 범위·확인 결과·복구 절차는 [Azure 배포 문서의 키·모델 교체 기록](azure-vm-deployment.md#openai-키색상-모델-교체-배포-2026-10-21)에 정리했다.


## 2026-10-15: 포스터를 참고한 새 배경 생성 (로컬 검증)

위의 10월 14일 기록은 포스터 자르기 좌표를 추천하던 당시의 동작이다. 현재 `OpenAiPosterBackgroundClient`는 공식 포스터를 Images Edit API의 참고 이미지로 보내고, 로고·문구·날짜가 없는 별도 배경을 생성한다. 원본 포스터를 그대로 반환하는 실패 대체 경로는 없다.

- `OPENAI_BACKGROUND_MODEL`: 기본 `gpt-image-1.5`. 해당 이미지 모델 사용 권한이 있는 API 키가 필요하다.
- `OPENAI_BACKGROUND_BASE_URL`: 기본 `https://api.openai.com/v1/images/edits`. 색상 추천용 Responses API 설정과 별개다.
- ticket: 어두운 글자에 맞는 밝은 가로 배경을 생성하고 800×360 JPEG로 맞춘다.
- closed: 밝은 로고·안내문에 맞는 어두운 세로 배경을 생성하고 720×1440 JPEG로 맞춘다. 내 정보 배경에도 사용한다.
- closed 프롬프트는 포스터의 색감과 분위기를 바탕으로 중앙을 비우고, 특징적인 장식 일부만 하단 한쪽에 작게 배치하도록 요청한다. 원본 포스터의 구도·문구·전체 질감을 복제하지 않으며 특정 축제나 꽃 이미지로 고정하지 않는다. 세로 크롭 후에도 장식이 남도록 안전 영역을 지정한다.
- 배경 생성 요청만 백엔드 150초, 브라우저·Nginx 180초로 제한한다. 색상 추천 요청 제한은 유지한다. 자동 유료 재시도는 하지 않는다.

대표색 추출 → 기준색 선택 시 색상 시안과 두 배경을 준비한다. 시안 선택·미리보기만으로는 배경을 저장하지 않는다. **3번 영역의 ‘전체 적용’**이 이미지 업로드 후 테마와 두 배경 주소를 함께 저장한다. 고급 설정의 ‘저장’은 색상 테마만 저장한다. 같은 페이지에서 기준색만 바꾸면 이미 생성된 두 배경을 재사용한다.

최신 PR #78의 `4e807f8`을 기준으로 로컬에서 실제 이미지 생성 두 요청의 HTTP 200, 관리자 ‘전체 적용’, 업로드 파일 HTTP 200, MySQL의 두 배경 주소, 새로고침 후 화면의 동일 이미지 참조를 확인했다. 공식 포스터·로고·홈 이미지와 티켓팅 회차는 유지했다. 티켓팅 OFF 화면 확인 후 운영 모드는 검증 전 상태로 복원했다. 이 추가 검증은 로컬 저장소 기준이며 Azure Blob 업로드나 운영 배포를 검증한 기록은 아니다.

후속 모바일 조정에서는 closed 배경만 다시 생성·저장하고 기존 티켓 배경·색상 테마·브랜딩·운영 설정이 유지되는지 확인했다. 390×844와 360×640 브라우저 화면에서 저장된 이미지 로딩과 안내·홈 버튼을 확인했으며, 실제 휴대폰 기기 검증과는 구분한다. 티켓팅 OFF 안내의 어두운 덮개는 약하게 조정하고 별도 검정 패널을 두지 않는다.
